## 1. 目标与原则

### 1.1 产品目标

交付本地多账号 Telegram 操作工具：会话导入、代理与节流、批量消息/群组/联系人/采集，以及可追溯的任务日志与导出。

### 1.2 产品期次划分

| 产品期次 | 对应工程阶段 | 目标 |
|---|---|---|
| **一期（MVP）** | P0～P4 | 本地核心能力可演示、可双端安装；**不依赖**用户注册登录与付费后端 |
| **二期** | P5（+ 评审通过的 C 系列） | 定时、统一收件箱、TDATA、养号、内容采集等增强 |
| **三期** | P7 | 注册登录、许可证、服务端风控规则、付费校验等 **依赖后端接口** 的边缘/商业化能力 |

> 说明：下文工程编号里的「P3」仅表示「MVP 业务层」任务包，与产品「第三期」不是同一概念。产品第三期对应工程 **P7**。

### 1.3 范围原则

| 类别 | 处置 |
|---|---|
| 已闭环（F 系列） | 进入开发 |
| 部分闭环（F 系列） | 补规格后进入对应阶段 |
| 候选 C01–C07 / 结果追踪 | **仅评审，不自动进 MVP**；通过后另开变更 |
| 未闭环：F05、F17、AI/CRM/转化、外部 API/CLI/Webhook | **明确不做**（对外开放 API/Webhook 仍不做；三期后端为 **自有商业化服务端**，不在此列） |
| 注册登录 / 许可证私钥 / 服务端风控 / 付费校验 | **第三期（P7）**；一期、二期不得把私钥或校验算法下发客户端 |

### 1.4 UI 风格原则（PC 微信风格）

整体视觉对齐 **PC 端微信**：干净、克制、白底为主，绿色承担主操作与选中态。

| 项 | 约定 |
|---|---|
| 页面背景 | 白色 / 浅灰分区（类似微信主区 `#FFFFFF`、侧栏浅灰） |
| 主色 / 按钮 | 绿色系主按钮、主操作（参考微信绿，建议设计令牌如 `--color-primary: #07C160`） |
| 选中 / 激活 | 列表项、侧栏菜单、Tab 选中使用浅绿底或绿色指示条 + 绿色文字/图标 |
| 文字 | 深灰主文、次级灰说明；避免大面积彩色字 |
| 边框与分割 | 细线浅灰分割，少阴影、少圆角卡片堆叠 |
| 布局参考 | **三栏**：左图标导航 + 中协议号池（可多选）+ 右工作区（详见 `Interaction-Logic.md`） |
| 状态色 | 成功用主绿；警告橙；错误红；等待/禁用用中性灰 |
| 禁止倾向 | 一期不做暗色主题默认；不用紫系渐变、大发光、密集胶囊标签 |

**落地要求：**

- P0 增补简易《UI 设计令牌》或在 MVP PRD 中写死色板与组件状态。  
- P1 工程骨架即按该风格搭布局壳与基础组件（Button / Menu / Table / Form）。  
- 后续业务页不得另起视觉体系。

### 1.5 工程原则

1. **一桌面客户端、多 TG 协议号**：用户侧只有一个软件客户端；其下管理 N 个协议号（Session）。协议层为 **一协议号 ↔ 一 gotd Client ↔ 一代理 ↔ 独立 `access_hash` 缓存**，禁止跨协议号复用实体凭据。不是「一协议号一个桌面窗口」。  
2. 日志区分：本地执行 / 接口接受 / 业务结果 / 未知。  
3. FloodWait 进入等待态并自动续跑，不伪装成成功。  
4. 发布为编译后的 sidecar 二进制；密钥本地加密，不上传 Session。  
5. 文案遵守竞品文档 §5 宣传边界（不承诺免限制、完整采集、阅读/转化等）。  
6. **敏感逻辑放服务端**：许可证私钥、付费校验算法、可变更风控规则仅存在于后端；客户端只持短期凭证或验签公钥。  
7. 一期默认 **离线可用**（无强制登录）；三期再叠加账号与授权门禁。  
8. 交互按 `Interaction-Logic.md`：左导航 → 中协议号池多选 → 右模块配置与任务提交。

## 5. P2 — MVP 平台层

对应闭环分析 §1.2 + 等待处理（部分闭环，本阶段必须落地最小集）。

| ID | 能力 | 要点 | 验收 |
|---|---|---|---|

| P2-2 | 协议号池 | 属性、状态、多选、筛选、任务占用；选中态合微信风 | 状态变更可刷新；与交互文档 §5.1 一致 |

| P2-4 | 执行节奏 | 间隔、并发、单账号上限 | 文案注明非官方额度 |
| P2-5 | 任务队列 | 同步最小状态机；可取消 | 中断后不静默重复 |

## 6. P3 — MVP 业务层（一期工程阶段，非产品第三期）

按依赖排序实现；每项完成后即写模块级验收用例。

### 6.1 实现顺序

```text
F11 账号检查 ──┐
F12 SpamBot  ──┼──► 账号可用性基线
               │
F19/F20 联系人 ──► F08 邀请联系人入群
F01/F02/F03 私信 ◄── 实体解析与缓存（D4）
F06/F07 加退群
F09 用户名加成员
F23 成员采集（标注来源）
F25 手机号检查（与 F02 共用解析）
```

### 6.2 模块清单与验收摘要

| 编号 | 功能 | 优先级 | 验收摘要 |
|---|---|---|---|
| F11 | 账号检查 | 必做 | 可用/失效/冻结可区分；检查通过 ≠ 全能操作 |
| F12 | SpamBot 状态检查 | 必做 | 多语言或兜底解析；超时可记录 |
| F01 | 按用户名发私信 | 必做 | 隐私/拉黑/停用错误分类 |
| F02 | 按手机号发私信 | 必做 | 五态结果，未匹配≠未注册 |
| F03 | 按用户 ID 发私信 | 必做 | 无 hash 明确失败；禁止跨号复用 |
| F06 | 批量加入群/频道 | 必做 | 审批/上限/链接失效可记录 |
| F07 | 批量退出群/频道 | 必做 | 成功失败可追溯 |
| F08 | 联系人加入群 | 必做 | 无权限/隐私拒绝可提示 |
| F09 | 按用户名加成员 | 必做 | 群/频道规则差异有说明 |
| F19 | 添加联系人 | 必做 | 导入结果字段完整 |
| F20 | 删除联系人 | 必做 | 列表与服务器侧一致可核 |
| F23 | 成员采集 | 必做 | **来源字段必填**（成员列表 vs 发言者） |
| F25 | 手机号检查 | 必做 | 与 F02 同一结果枚举 |

### 6.3 一期不做（再次确认）

- F05、F17  
- AI / CRM / 转化统计  
- 对外 API / CLI / Webhook  
- C01–C07（除非评审书面纳入二期）  
- F04/F10/F13/F18/F21/F22/F24 及 TDATA 导入（归二期 P5）  
- F14/F15/F16（低优先级，可穿插在 P4 后或 P5）  
- **注册登录、许可证签发、服务端风控规则下发、付费校验算法（归三期 P7）**

**P3 出口：** 上表 13 项业务 + P2 平台在 Win 与 mac 各至少完整跑通一轮。

## 10. P7 — 第三期：商业化与后端依赖能力

一期、二期以 **本地 sidecar + SQLite** 完成业务；下列能力依赖 **自有后端**，统一放在第三期，避免把密钥与算法打进客户端。

### 10.1 范围清单

| 编号 | 能力 | 客户端职责 | 后端职责（必须） | 说明 |
|---|---|---|---|---|
| B01 | 用户注册 / 登录 | 登录页、Token 存储、会话过期处理 | 账号体系、鉴权、刷新令牌、风控登录 | 一期无强制登录；三期可配置「必须登录后可用」 |
| B02 | 许可证管理 | 展示授权状态、到期提醒、激活码录入 | **许可证私钥仅存服务端**；签发/吊销/续期；下发短时许可证或签名断言 | 客户端最多持有验签公钥或短期 license token |
| B03 | 付费与订单校验 | 拉起购买页/展示套餐、展示支付结果 | **付费校验算法与支付密钥仅存服务端**；验单、开通权益、防重放 | 客户端不得内置「算出来就算过」的校验逻辑 |
| B04 | 服务端风控规则 | 拉取并执行已下发的限制策略（如并发上限、模块开关） | **规则配置与变更在服务端**；审计日志 | 区别于 Telegram 侧 FloodWait；此为产品自身运营风控 |
| B05 | 授权门禁与模块开通 | 按权益隐藏/锁定模块入口 | 权益与 SKU 映射、灰度开关 | 与 B02/B03 联动 |
| B06 | 设备绑定 / 激活数限制（可选） | 上报设备指纹（最小化） | 绑定策略、超限拒绝 | 需隐私说明 |
| B07 | 在线更新通道与强制更新策略（可选） | 检查更新、下载安装包 | 版本清单、签名校验、灰度 | 可与二期「更新支持」衔接，鉴权部分放三期 |

### 10.2 安全红线（三期必须遵守）

1. **许可证私钥、支付密钥、付费校验算法、可变风控规则源数据** 不得进入安装包、 sidecar 或前端资源。  
2. 客户端只接收：**短期 Token / 已签名的 license 断言 / 已编译的策略参数（无密钥）**。  
3. 断网策略需产品明确：例如「宽限期 N 天」或「仅只读本地已有数据」——写入 PRD，禁止模糊实现。  
4. 三期后端与「明确不做的对外 API/Webhook 开放能力」无关：后端仅服务本客户端商业化，不对外提供开放平台。

### 10.3 建议子阶段

| 子阶段 | 内容 | 出口 |
|---|---|---|
| P7-a | 后端选型与账号/许可证数据模型；OpenAPI 草图 | 接口评审通过 |
| P7-b | 注册登录 + Token；客户端登录页（仍保持微信风） | 可登录并刷新 |
| P7-c | 许可证签发/激活/到期；模块门禁 | 无有效许可时行为符合 PRD |
| P7-d | 套餐、支付验单、权益开通 | 沙箱支付全流程通过 |
| P7-e | 服务端风控规则下发与审计 | 改规则无需发版客户端即可生效 |
| P7-f | 断网降级、安全审计、渗透与密钥托管检查 | 上线检查清单通过 |

### 10.4 依赖与前置

- 建议在 **一期 MVP 稳定** 后再启动 P7-a，避免商业化耦合拖慢核心业务。  
- 二期功能（P5）可与 P7 并行，但 **许可证门禁** 若启用，需先有 B01/B02。  
- 需新增文档：`商业化后端 PRD`、`License 与支付接口说明`（P7 启动时编写）。

**P7 出口：** 后端生产可用；Win/mac 客户端完成登录→购授权→模块解锁联调；安全红线审计通过。

- [ ] 手机号检查五态结果正确，未匹配不标成未注册。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Telegram API / 风控变化 | 模块突然失败 | 错误码可扩展；gotd 跟进 layer；文案不承诺稳定额度 |
| FloodWait / PeerFlood 频发 | 批量任务体验差 | 节奏默认保守；waiting 可视化；单账号熔断 |
| 实体跨协议号误用 | 串号、发送失败 | D4 强制隔离；单测覆盖 |
| gotd 与桌面 Session 兼容 | 导入失败 | 明确支持格式矩阵；失败可诊断 |
| Win/mac 打包与 sidecar 路径 | 无法分发 | P1 即验证捆绑；P4 干净机回归 |
| 范围膨胀（C 系列/二期/三期） | 延期 | 期次隔离 + 变更单；一期出口刚性 |
| 客户端塞入许可证/支付逻辑 | 破解与合规风险 | 三期红线；代码审查禁止私钥与本地「伪校验」 |
| UI 风格漂移 | 体验不统一 | D6 令牌 + P4 视觉回归 |
